SEO Audit Engine.

An evolving SEO research and auditing system intended to connect technical website observations with search demand, business value and practical improvement priorities.

SURAJ KUMARWORKING PROTOTYPE / EXPANDINGLAST REVIEWED 2026-11-14

Why I wanted a different kind of SEO audit

Many SEO audit tools generate a long list of issues without answering the question the business needs most: which fix should happen first, and why? A missing description on an obscure page, a broken canonical on an important service page and a slow conversion journey may all appear as warnings, but they don't carry equal business impact. The project started from the desire to connect technical findings with user intent and meaningful priorities.

I wanted an audit that considers what a page does for the organisation, the search demand it already captures and the resources required to fix it. This is harder than counting errors because it combines deterministic crawling with judgment about content and business relevance.

Core auditing pipeline

The architecture uses an application interface, backend crawl processing and a PostgreSQL-backed record of jobs and findings. Render and Neon have been part of the deployment. A basic crawl can inspect metadata, headings, internal links, status responses, canonical values and indexability clues. Future browser rendering expands the work to pages that rely heavily on client-side JavaScript.

Every observation should retain the source URL, checked time and evidence. If a page cannot be fetched, that is a result worth reporting rather than a reason to fabricate a title or meta tag. Crawl limits, provider restrictions and timeouts need to be visible to the person reading the report.

Integrating performance with technical signals

Search Console can add useful context: which pages receive impressions, which query groups matter, and where low CTR or declining visibility warrants investigation. It does not directly tell a tool why a page ranks as it does or which fix will produce revenue. The opportunity model should therefore distinguish measurement from recommendation.

For example, a page with relevant impressions, weak click-through and incomplete service information may deserve a content review. A technically broken page that supports an important service may deserve immediate repair. A low-traffic archived page might be less urgent even if an audit finds several small warnings. Ranking these requires a transparent model of impact, confidence, effort and business relevance.

The challenges beyond a basic crawler

Scaling from a small crawl to thousands of URLs changes infrastructure requirements. Rate limits, rendering costs, duplicate content, parameterised URLs and queue management must be handled. JavaScript-rendered pages need a controlled browser environment, and Search Console OAuth requires careful token management and access scoping across client accounts.

Historical comparisons create another layer: the system must know whether an issue improved, whether a URL disappeared, and whether apparent progress comes from a changed data scope. AI-based recommendations can help explain patterns but must be grounded in the actual crawl and performance data. Unsupported diagnosis should not be presented as a verified defect.

What a client-ready output should explain

Good output groups findings by priority and category, provides a reproducible explanation and suggests concrete next steps. Each recommendation should link to the affected URL, show the observation, explain the risk and provide a verification method after implementation. A visual progress bar may improve the experience of waiting, but the final report must be accurate enough to support real work.

I also want the report to separate technical blockers from content opportunities and low-confidence hypotheses. When a site owner receives fifty findings, the interface should make it easy to focus on the first five meaningful changes rather than celebrating the length of the list.

Status, limitations and next questions

The project has had a functioning web deployment and an evolving feature plan. Areas of continuing work include deeper rendering checks, larger URL limits, OAuth multi-account support, richer query analysis, historical comparisons, AI recommendations and platform-specific integration. Not every listed idea is a finished capability. That distinction is important to users comparing a concept with a production audit suite.

The central design question remains the same: how can we reduce the distance between finding a problem and making a good decision? The answer will come from reliability, clear evidence and prioritisation—not from adding more warnings to an already noisy dashboard.
