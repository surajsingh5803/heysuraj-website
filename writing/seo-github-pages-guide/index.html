SEO on GitHub Pages: A Practical Guide From Domain Setup to Search Console

A practical guide to GitHub Pages SEO covering custom domains, HTTPS, metadata, canonical URLs, sitemaps, Search Console, indexing, internal links and content quality.

SURAJ KUMAR2026-11-144,611 WORDS

This guide comes from the practical decisions behind building a personal website on GitHub Pages. It is written for people who want control of their content and search visibility without buying a heavy hosting stack. We'll go from domain and deployment to indexing, measurement and editorial decisions, including the mistakes that are easy to make when you first launch.

Why a static personal site can be the right decision

When people first think about a personal website, they often imagine a paid hosting plan, a page builder, a database and a collection of plugins. None of these is automatically necessary. A site that explains who you are, what you have built and how to contact you can be delivered as ordinary HTML, CSS, JavaScript and images. A static site is not a second-class website. It is a simpler publishing model with a different operational trade-off: fewer moving pieces, but more responsibility for how you organise and update files.

My own project, HeySuraj, started as a personal-brand domain and a GitHub Pages repository. The appeal was not only the price. I wanted to edit the real files, understand how the domain resolved, choose my metadata deliberately and be able to change the design without maintaining a server. That choice let me focus on clarity and interactivity rather than infrastructure. It also made me confront an important truth about search optimisation: a website can look excellent, serve securely over HTTPS and still be unknown to Google until it is discovered and evaluated.

Static hosting is best suited to content-focused portfolios, documentation, small publications and business information sites that do not need complex server-side processing. A membership product, a secure client portal or an application handling private records has different needs. Decide which problem your site must solve before choosing a stack. A technology decision is valuable when it removes friction from the goal, not when it makes the project sound more advanced.

Choose the domain for people, not just for a keyword

Domain naming becomes easier when you understand that a domain is an address and a brand cue, not an automatic entitlement to search rankings. I chose heysuraj.com because it was easy to say, easy to remember and broad enough to cover marketing, AI, entrepreneurship and creative experiments. A narrow keyword domain would have locked the identity more tightly to one service. A personal website can evolve over years, so that flexibility matters.

The extension deserves practical thought. A .com domain is familiar to many audiences, but a relevant .in or other country domain can work when the audience and identity justify it. There is no magic extension that replaces useful content or reputation. What matters operationally is that you control the registration, understand its renewal price, can edit DNS records and can keep it active. Check the normal renewal price before paying for a discounted first year; a low introductory fee does not necessarily imply a low long-term cost.

Use the exact domain consistently in your navigation, canonical URLs, Search Console property, sitemap and professional profiles. If a similarly named business appears in search results, that is not proof that something is broken. Search engines initially need stronger signals to associate your name with your actual identity. Your About page, social profile links and original project material make that association more concrete than repeating the brand name dozens of times in headings.

Create a GitHub repository that has a clear job

For a basic GitHub Pages site, a public repository can hold your website files. The important thing is not the repository name but its layout and publishing configuration. Put your homepage at the repository root as index.html when you deploy directly from the main branch root. Keep CSS, scripts and images in named folders. A README should explain what the project is, how to update content and what should never be committed. Never put credentials, private customer data, API tokens or an environment file containing secrets into a public repository.

A useful minimal layout is index.html, assets/style.css, assets/app.js, robots.txt, sitemap.xml, CNAME and a custom 404.html. If you add independent pages, use folders such as about/index.html and writing/index.html, which produce readable paths like /about/ and /writing/. Static site generators can reduce repetition across a larger collection of pages, but you do not have to adopt one before you have content worth publishing.

In GitHub, navigate to Settings and then Pages. Choose the publishing source that corresponds to your repository structure. For straightforward sites, deploying from the main branch root is easy to understand. After committing files, check that the Pages build has completed and that a live URL loads the latest version. A commit existing in the repository does not mean visitors can already see it; deployment is a distinct step. This distinction is important when you are troubleshooting a missing update, a cached image or a newly added article.

Connect the domain without breaking DNS

DNS is where a domain name is associated with the infrastructure serving the website. For an apex domain such as heysuraj.com, GitHub Pages supports specific A records that point to its service. For the www hostname, a CNAME normally directs that host to the appropriate GitHub Pages hostname. The exact instructions should always come from GitHub's current custom-domain documentation, because these are operational settings you should not improvise.

When editing DNS, identify which records already exist and why. Do not delete MX records that support email, SPF or DKIM TXT records that protect outbound mail, or unrelated subdomain entries simply because you are configuring your website. A domain can simultaneously support a personal homepage, email service and additional subdomains. Treat each record as part of a working system. A rushed edit can disconnect services that appear unrelated from the Pages setup.

DNS changes are distributed rather than instant. TTL values influence how long existing answers may be cached; propagation and certificate checks can take time. If GitHub reports a failed domain check immediately after adding the correct records, inspect the current records and wait for them to be seen before making more changes. Repeatedly replacing correct values creates new uncertainty. Once GitHub shows the domain is configured, keep the CNAME file in your repository and avoid unrelated DNS changes.

Treat HTTPS as essential infrastructure

HTTPS protects the connection between a visitor and the website. It is a baseline expectation for any credible personal brand, not an optional marketing enhancement. GitHub Pages can provision a certificate for a correctly configured custom domain. During initial setup, the Enforce HTTPS checkbox may be unavailable while that certificate is issued. An unavailable checkbox during provisioning is different from a permanent technical failure.

After the certificate is active, enable HTTPS enforcement and test the site at both the apex and www variants as relevant. Check that the browser loads the secure version without a warning and that navigation, fonts, images and scripts are also served through secure URLs. Mixed-content problems can cause browser warnings or blocked resources. If you embed external images or scripts, make sure those references use HTTPS and are from sources you trust.

Don't confuse the presence of a browser padlock with proof of SEO readiness. HTTPS is a necessary technical foundation, but search engines still consider whether they can crawl the content, understand the page, select a canonical URL and assess its usefulness. A technically valid website can remain unindexed for reasons unrelated to SSL. Troubleshoot the actual layer that is failing rather than changing every configuration at once.

Build the site architecture around real topics

A personal website does not need thirty navigation items to look substantial. Start with a simple path that explains the person, their work, their projects, their ideas and a way to connect. An ideal visitor should be able to answer three questions quickly: who is this person, what can they demonstrate, and why might I want to learn more or contact them? Everything else should support those answers.

There is an important difference between an on-page section and a dedicated page. A section linked as #projects is useful for exploration, but it is part of the homepage rather than a standalone document with its own search title and canonical URL. If a project merits detailed explanation, giving it an individual page allows you to describe the problem, constraints, decisions, implementation and lessons without overloading the homepage. Likewise, a full article should have a stable, crawlable URL and a genuine editorial structure, not just a JavaScript popup that only displays a title.

Use readable paths such as /work/, /about/ and /writing/ rather than opaque IDs. Name routes for their subject, not for the number of keywords you can fit into them. Make the main content available in HTML and connect pages with ordinary anchor links. Google explains in its SEO Starter Guide that clear site organisation and contextual links help both visitors and search systems understand how content fits together.

Write page titles and descriptions for real search intent

Every important page should have its own meaningful title element. On a personal homepage, identifying the name and professional focus matters more than a poetic slogan alone. A title such as “Suraj Kumar (Hey Suraj) | Digital Marketing, AI & Building” tells a searcher both whose page it is and what subjects they are likely to find. An About page can focus on the person's background, while a practical guide should describe the specific problem it answers. The content on the page must justify what the title promises.

Meta descriptions are not a guaranteed ranking lever and Google may generate its own snippets. They are still useful opportunities to summarise relevance and invite the right visitor. Write natural descriptions, not lists of disconnected keyword variants. A description for a guide about GitHub Pages SEO should make it clear that the page covers domain setup, crawlability, indexing, sitemaps and common mistakes. A description for a project page should be specific about the experiment and its status.

Use one clear primary heading and sensible section headings. These create a readable hierarchy; they are not a reason to repeat the same phrase at every level. Descriptive alt text should communicate the meaning of images rather than stuff them with place names or service terms. If an image is purely decorative, an empty alt attribute is often more appropriate. Search optimisation should make the page easier to use even if there were no search engine evaluating it.

Use canonical URLs to avoid confusing duplicates

When a site has both https://heysuraj.com and https://www.heysuraj.com, the same content may be reachable through several variants. A canonical link communicates which URL you prefer search systems to treat as the main one. It is a strong hint, not a rule that forces a search engine to select your version in every case. Consistent internal links and redirects reinforce the same preference.

For a static site, include an absolute canonical URL in the head of each indexable HTML document. The homepage should identify its preferred homepage URL. Each article should identify its own final URL, not point back to the homepage. A common mistake is copying an identical head section into every page and forgetting to update the canonical value. That can inadvertently tell search systems that useful standalone pages are duplicates of a different page.

Check canonicalisation after deploying. Inspect the address bar, the HTML source and Search Console's user-declared and Google-selected canonical fields when available. For unusual cases, use Google's canonical URL guidance as the source of truth. Do not attempt to solve a ranking problem by setting arbitrary canonical tags. A canonical is for duplicate or near-duplicate URL consolidation, not for granting ranking preference to an unrelated article.

Understand the difference between robots.txt and noindex

A robots.txt file is a set of crawler instructions served at the root of a site. For a public personal website, a simple file allowing crawlers and pointing to the sitemap may be sufficient. It does not make the site appear in Google, and it should not be treated as an SEO booster. Its main purpose is crawl access management. As your site grows, you may use it to manage some kinds of crawler behaviour, but broad blocks can do more harm than good.

One subtle mistake is trying to hide a page from search by blocking its URL in robots.txt. A crawler that is forbidden from fetching the page may never see the noindex tag inside it. If a public page should be excluded from search, it is generally better to let the crawler access that page and provide a noindex directive. If content is genuinely private, use proper authentication and access controls. Noindex is not a security mechanism.

For editorial drafts, do not create an indexable article page that looks finished but contains a few paragraphs of placeholder text. Keep drafts unpublished until they provide real value. A list of planned articles may be useful to your own roadmap, but it should not be mistaken for a library of published resources. Search systems and readers are both better served by a smaller collection of complete, accurate material than a large set of thin pages designed to increase URL counts.

Create a sitemap that contains canonical, publishable URLs

A sitemap is a discovery aid. It helps search engines identify the URLs you want them to consider for crawling, especially on a new site with few incoming links. The sitemap should list canonical, indexable pages using complete HTTPS URLs. You can start with a one-URL sitemap for a single-page site. As you add About, Work and articles, add those pages and remove entries for deleted or unpublished content.

Keep the XML valid, serve it with an accessible HTTP response and link to its location in robots.txt. A minimal sitemap has a urlset root and one url element per relevant location. You do not have to add speculative priority scores or change frequencies. If you include lastmod, it should represent meaningful changes to that page rather than update automatically every time you rebuild without changing its content.

Submit the sitemap through Google Search Console. The important distinction is between a successful submission and actual indexing. Search Console may initially report “Couldn't fetch” or a temporary processing error while the service catches up. If the file opens in a browser and the live server is returning it correctly, investigate the report before endlessly changing the XML. Google's sitemap documentation is clear that discovery does not guarantee indexing or ranking.

Verify Search Console and learn what its reports mean

Google Search Console is the most important free diagnostic tool for a new site because it reports how Google sees the property. A domain property generally requires a DNS TXT verification record. Copy the full value supplied by Google into the DNS provider's TXT record field. The host field for the root is often shown as @, but the interface may display the domain differently. Do not overwrite an unrelated SPF record simply because both use TXT type: a DNS zone can contain multiple TXT values.

After verification, inspect the homepage using the exact canonical URL. Search Console distinguishes Google Index information from Live Test information. “URL is available to Google” in a live test means Google could access a current version and the page appears eligible for indexing. It does not mean the page is already included in the search index. “URL is on Google” in the indexed inspection view is the clearer confirmation that the selected URL has been indexed.

My own setup experience reinforced the value of checking the date of the last crawl. When a recently purchased domain displays an older crawl timestamp, that report can reflect earlier use of the domain rather than the current website. A newly launched page should be evaluated through the live test and, later, the updated index report. Don't mistake historical signals about a domain for a definitive diagnosis of the latest code.

Why passing a live test is not a ranking guarantee

Indexing involves discovery, crawling, rendering and a decision about which content to include. A page can be fetched successfully yet remain outside the index. New sites need time to establish a crawl pattern and show why their material deserves inclusion. Repeatedly requesting the same URL does not create more authority or guarantee a faster result.

If a page is marked “Crawled – currently not indexed,” check whether it is the right version, whether the content is complete, whether it duplicates another page and whether it provides something useful beyond a generic introduction. Technical errors should be fixed when present, but not every non-indexed URL has a technical defect. A thin, near-duplicate or low-value page can be left out even when its sitemap and canonical tags are valid.

Search Console allows indexing requests through URL Inspection, but use them selectively after important changes. Then track the indexed URL and query performance over time. Google says in its recrawling guidance that crawl requests are not guarantees. Your actual work is to make the page technically accessible, meaningfully linked and genuinely useful. A request is simply a prompt for another look.

Internal linking on a small personal site

Internal linking does not have to be complicated to be valuable. Your About page should link to the work and projects that support its claims. The Work page should link to relevant methods and articles. A guide about Search Console should reference a deeper guide on indexing when the question arises naturally. A project describing a lead-intelligence system should connect to your writing about qualification and data accuracy. Those links form readable paths that give visitors a reason to continue.

Use anchors that describe the destination. “Read how I approach Google Search Console analysis” is more informative than “click here.” Avoid putting the same list of every article into each paragraph. Too many unrelated links can distract readers and dilute the information hierarchy. Context is more important than raw count. A related-articles block at the end is helpful, but the strongest links often appear within the explanation at the moment a reader needs the additional detail.

Because this site is static, links can be written directly as normal anchor elements. That is an advantage for crawlability and a simpler fallback if JavaScript fails. You can still use JavaScript for search, filtering, interactive effects and preferences, but don't hide your important page relationships behind buttons that only change local state. A browser and a crawler should both be able to find the essential documents without guessing how the interface works.

Make animations an enhancement rather than a requirement

A modern personal site can have ambitious interactive design. The challenge is keeping motion, font loading and scripts from making content difficult to reach. Start with real HTML for the primary message. Load images responsibly, reserve their display space and reduce oversized assets. Use a small number of well-chosen typefaces and avoid making the page rely on a heavy client-side framework when simple static markup will do.

On HeySuraj, the visual design uses atmospheric animation, project cards and theme controls. Those features support the experience, but they shouldn't determine whether somebody can read the headline, learn about the work or use the contact links. Reduced-motion preferences deserve respect, particularly when a page includes background particles or moving visual elements. A still mode is more considerate than forcing visitors to accept a particular effect.

Check page performance on mobile as well as desktop. A fast laptop over Wi-Fi may hide problems that matter on an older phone. Look for delayed text rendering, cumulative layout shifts, inaccessible navigation and JavaScript errors. The best optimisation is not always minifying another file; it may be removing a component that adds little value relative to the work it forces the browser to perform. Design quality includes restraint.

Structured data for a personal author and articles

Structured data is a machine-readable description of content. On a personal site, Person markup can connect a name, canonical website, professional focus and verified social profiles. On an article, BlogPosting markup can describe the headline, author, publication date, page URL and relevant category. BreadcrumbList markup can clarify the route from Home to Writing to a specific guide. These are opportunities for clearer interpretation, not guarantees of prominent search features.

Keep structured data aligned with what readers can actually see. Do not declare awards, professional credentials, reviews or business entities that are not established on the page. Use the same name across your author bylines, About page and social profiles, and link to the actual pages you control. If a particular person has multiple online identities, a consistent canonical homepage and legitimate profile references make it easier to distinguish them.

Validate the JSON-LD syntax before deploying. Recheck after major template changes because an escaping error can break a page's structured data without visibly affecting its design. For articles, Google's Article structured data documentation explains recommended properties. Structured data should describe good content; it cannot substitute for the quality, originality or usefulness of the underlying page.

Build reputation through relevance, not backlink quotas

New site owners often ask how to get thirty, fifty or one hundred backlinks quickly. The question is understandable but can lead to low-value work. A link is valuable when it helps a person discover a relevant resource and accurately represents a connection. A genuine link from your own LinkedIn profile, a technical project repository, a professional biography or a publication that finds your work useful is more credible than dozens of directory profiles created only to manipulate ranking signals.

Start with assets and relationships you already have. If a GitHub repository contains a useful open-source project, link to its detailed explanation on your site and link back from the project documentation where it adds context. If you publish an original guide with screenshots and reproducible steps, share it with the communities where people actually need that information. If a collaborator or professional organisation lists your involvement, a correct profile link can help both readers and search engines.

Avoid mass automated forum replies, paid passing-PageRank placements, excessive reciprocal links or low-quality directories. Google documents these patterns under its link spam policies. Outreach should offer something useful to the receiving site: a relevant resource, verified work, original data or an opportunity to collaborate. Keep a record of which links were genuinely published rather than reporting outreach attempts as completed backlinks.

Publish content around work you can explain

The most defensible editorial strategy is to write about things you can test, demonstrate or analyse with care. For this site, that includes setting up GitHub Pages, using Search Console, improving service-page SEO, measuring marketing performance, experimenting with AI assistants and learning from software prototypes. Each subject can support detailed articles because it connects to actual projects and practical decisions.

Don't make word count the goal. A four-thousand-word guide may be appropriate if it explains a complex workflow with examples, edge cases, decision tables, common failures and useful references. A question that can be answered clearly in six hundred words should not be stretched into four thousand. Depth is the amount of useful information delivered, not the physical length of the text. Google warns against scaled publishing with little original value even when the words are technically different.

Build an editorial process: identify the reader's real question, check current source documentation, gather original examples, outline the decision path, draft, verify facts, add useful internal links, review for repetition and publish when complete. Update content when a platform changes. A smaller library that a reader trusts is a better foundation for a personal brand than an enormous collection of articles that could have been written under anybody's name.

Troubleshoot in layers rather than changing everything

When something doesn't appear as expected, resist the temptation to change DNS, metadata, design and sitemap settings simultaneously. Begin with the actual symptom. Does the URL load in a browser? Is the certificate valid? Does the server return the right content? Is the page present in the GitHub repository? Has the latest commit been deployed? Does the browser cache an older version? Does the live inspection retrieve the expected page? Each answer narrows the problem.

For a missing image, inspect the resource path, filename case and file format first. For a broken article page, confirm the directory contains an index.html file and that the navigation points to the correct absolute path. For a sitemap error, load the sitemap directly and check the response, syntax and URLs. For indexing uncertainty, compare the live test with Google's stored index status. For a ranking concern, examine query data and content relevance instead of treating the absence of a manual search result as proof of technical failure.

A written deployment checklist helps: source files committed, build passed, homepage responsive, internal links valid, HTTPS active, canonical values checked, sitemap updated and Search Console inspection reviewed when needed. It takes more discipline than repeatedly clicking Request Indexing, but it makes the website easier to maintain and reduces the chance of breaking something that already works.

A realistic first ninety days after launch

In the first phase, get the foundations right: domain setup, HTTPS, a clear introduction, contact methods, Search Console access, a sitemap and at least one useful explanation of your work. In the next phase, make the site more informative with dedicated About and Work pages, projects described honestly, and a small collection of original articles. Links from your genuine profiles help people discover it. A personal website with an authentic voice becomes more useful each time it answers another relevant question.

Later, use Search Console's Performance report to see which queries generate impressions, which pages attract visitors and whether the search appearance matches the intended subject. Watch the trend over meaningful periods rather than checking rank positions in an incognito tab every hour. A manual branded search can confirm that your page appears, but personalised results and location can vary. Query and page reports provide a better basis for deciding what content to deepen.

My preferred measure of progress is not only impressions. I want the site to explain my work more clearly, help a visitor understand a project, and create more qualified conversations. Search performance should support that goal. The design may keep evolving, but the strategy remains straightforward: build something useful, document the thinking, verify that people and crawlers can reach it, and improve based on evidence rather than anxiety.

A launch checklist you can reuse

Before declaring a static personal site complete, review the following questions in order. Can a visitor immediately tell who owns the site and what they do? Does every primary navigation link work? Are your projects labelled with truthful statuses? Can somebody contact you without searching through unrelated platforms? Is the mobile layout usable and comfortable to read? Are images appropriately sized and do motion preferences work?

Next check the technical layer. Does your preferred HTTPS URL load consistently? Do any obsolete http or www variants redirect appropriately? Is your custom-domain configuration still present? Does each indexable page have its own descriptive title, canonical and useful main heading? Are robots.txt and the sitemap accessible? Are draft pages excluded from the sitemap? Can you open an article directly by its URL and still reach the homepage and the article library?

Finally check the publishing system. Is there a repeatable way to add a page and update internal links? Are code changes reviewed before publication? Are secrets excluded from the public repository? Do you know where Search Console reports indexing or performance concerns? Are you keeping a record of original examples and credible sources for your articles? If those answers are satisfactory, you have something better than a one-time design project: a personal publishing foundation that you can realistically maintain.
